# Write the project's Product Backlog as user stories

Theoretical Recap: User Stories and the Product Backlog A Product Backlog is the single source of truth for an agile development team, containing all the work needed on a product. It is a prioritized list of features, functions, requirements, and fixes, expressed as user stories. A user story is a simple, concise description of a software feature told from the perspective of the end user. They follow a standard template: "As a [type of user], I want [some goal] so that [some reason/benefit]. This format forces clarity on the actor, the action, and the underlying business value. The mental model is to see each story as a promise for a future conversation that elaborates the details through acceptance criteria. Common mistakes include writing stories from a technical or system perspective instead of a user's, creating overly broad "epics" without a clear path to smaller tasks, or forgetting the "so that" clause, which obscures the real business value. Another frequent error is writing acceptance criteria that are vague or untestable. Mini-example: For an online shop, a raw need might be "users must log in." A proper user story is: "As a registered customer, I want to log into my account so that I can access my order history and saved payment methods." Acceptance criteria could be: • After entering correct credentials, the user is redirected to their account dashboard. • After entering incorrect credentials, a clear error message is displayed.
