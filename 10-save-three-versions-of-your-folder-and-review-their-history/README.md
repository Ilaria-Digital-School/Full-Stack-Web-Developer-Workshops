# Save three versions of your folder and review their history

Theory Recap: Git Commit as a Saved Milestone A Git commit is a snapshot of your project folder at a specific moment. Think of it as saving a complete copy of every file, along with a message explaining what you changed. Each commit has a unique identifier, the SHA-1 hash, which acts like a permanent label in the history. Your repository is a timeline made of these commits. Your working folder is your active workspace, the 'staging area' (or index) is where you prepare a group of changes, and the 'head' points to your latest commit. Each new commit points back to its parent, building a chain. A common mistake is committing many unrelated changes under a vague message like "fixed bugs." Another mistake is forgetting to add new files to the staging area before committing. For a mini-example, imagine you have a file, notes.txt, with the single line "Start." Committing saves "Version 1." You edit it to "Start.\nAdded client list," stage, and commit. That's "Version 2." Your history now shows two points you can return to anytime.
